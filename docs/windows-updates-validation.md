# Проверка обновлений в Windows

30 октября 2026 года проверены один Windows 11 Pro x64 10.0.26300, Edge 156.0.4314.50, Python 3.13.17 из пакета и настоящая Станция Лайт 2 с готовыми root и SSH. Проверки установщика и голосового клиента описаны [отдельно](windows-validation-20261030.md).

## Установка и восстановление

- Настоящий установленный `alisa.cmd` обновил приложение из ZIP с SHA-256. Новая версия запускалась без перезагрузки Windows.
- Несовпадение версии manifest и запущенной программы вызывало откат. Внешняя блокировка папки Windows также оставляла прежнее приложение и понятный результат ошибки.
- Синтетические аккаунт, настройки, SSH и профиль браузера сохранялись. Неизвестные файлы прежнего приложения и предыдущие резервные копии оставались на месте.
- Очистка удаляла только неизменённые собственные временные файлы. Занятая DLL удалялась при следующем запуске после освобождения; изменённые и посторонние файлы сохранялись.
- Git-копия и неподходящая папка приложения не заменялись. Отказ SSH до начала транзакции не менял установленную программу.

## Меню

В настоящем терминале проверены «Обновить», «Не сейчас» и «Больше не спрашивать». Отключение предложений сохранялось между запусками, ручная проверка оставалась доступной. Переключатель уведомлений сохранял выделение строки; Esc отменял диалог без Traceback.

Для проверки меню транспорт метаданных GitHub направлялся на локальный тестовый ответ. Выбор, проверка ZIP, замена приложения, worker и возвращение CLI выполнялись настоящим кодом. Контролируемая недоступность GitHub не мешала открытию CLI. Эти проверки не выдаются за загрузку ещё не существовавшего тогда публичного релиза.

## Код возврата Windows

В первом прогоне обнаружено, что `os.execv` завершает старый Windows-процесс с кодом 0, пока updater продолжает работу отдельно. Поэтому вызывающая CMD могла принять откат за успех.

Исправленный `alisa.cmd` запускает управляющий процесс вне заменяемой папки `app`. Он ждёт освобождения старого CLI, запускает worker и возвращает его результат: `complete` — 0, `rolled_back` и `recovery_needed` — 1. Повторное открытие меню не стирает ошибку обновления.

Для перехода со старого launcher один раз нужен исправленный установщик и новый запуск CLI. Прямой `python alisa.py update` в Windows отклоняется до изменений и предлагает установленный `alisa.cmd`. Linux использует прежнюю передачу через `exec`.

В проверках настоящий `alisa.cmd` правильно возвращал коды при успешной замене, неверной версии, ошибке компонентов и неполном восстановлении. Дополнительно проверены обычный код команды 7, аргументы с кириллицей, пробелами и кавычками, повторное открытие меню и сохранение изменённого launcher.

## Настоящая колонка

- Фазы `connecting` и `active` отклоняли обновление до остановки и замены компонентов.
- В `idle` компоненты обновлялись, ранее работавший native возвращался в `idle`. Ранее остановленный режим сам не запускался.
- При контролируемой потере SSH после замены Windows-программы приложение откатывалось, а недоступные компоненты получали честный результат `recovery_needed`. После восстановления доступа клиент вернули в исходное рабочее состояние.
- Проверены живые неудачный и успешный кандидаты: `rolled_back/1` и `complete/0`.
- Аккаунт, чаты, SSH, фразы, подсветка, VPN-конфигурация и исходные флаги автозапуска сохранялись. Автоматического GPT-разговора обновление не включало.

## Автотесты и границы

На Windows прошли 29 host-тестов, 17 updater-тестов, 64 переносимых и 10 дополнительных проверок. Один Linux worker-тест пропущен по платформе; 11 Linux/mock-случаев явно исключены из переносимой выборки и не объявлены прошедшими. Повторный прогон 29 Windows host-тестов под Wine также прошёл.

Windows 10, отдельный прогон Chrome, живой Go, аппаратная Лайт 1 и её программная кнопка микрофона в GPT не подтверждены этим прогоном. Контролируемый отказ SSH не является испытанием потери питания. Windows-мост не реализован. Новая политика допуска неизвестной прошивки проверялась отдельно на фикстурах; эти результаты не подтверждают звук на каждой прошивке.
