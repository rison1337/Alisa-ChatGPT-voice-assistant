# Нативный голос и split tunneling

Проверка `alisa native network` определяет внешний IP запроса к сервису геолокации. При split tunneling этот маршрут может отличаться от маршрутов ChatGPT и STUN. Проверка HTTP или страны не подтверждает доступность голосового UDP.

По умолчанию нативный клиент собирает ICE-кандидаты через `stun.l.google.com:19302/UDP` и ожидает завершения до 12 секунд. `ice_gather_timeout` возникает до обмена SDP с голосовым сервисом; повторный вход не устраняет эту ошибку.

## Необязательный повтор без STUN

С версии 0.3.7 в настройках нативного режима можно отключить STUN-сервер. При `ice_gather_timeout` интерактивная проверка предлагает повтор без STUN; согласие пользователя требуется до повтора. Выбор сохраняется только после подтверждённого голосового ответа, при неудаче прежняя настройка восстанавливается. Обычный запуск не меняет её автоматически. Старый клиент без поддержки этого параметра требует обновления перед запуском с отключённым STUN.

Без STUN используются оставшиеся ICE-кандидаты; в некоторых сетях этого недостаточно для соединения. Настройка не отключает VLESS, запрет прямого выхода при его отказе или явную привязку к TUN. При исправной сети оставьте исходное значение. Работа повтора подтверждена автором PR #12 на одной Мини 3; это не подтверждение для всех NAT и VPN.

## Проверенный случай на Мини 2

В клиенте 0.3.5 при внешнем split tunneling DNS возвращал синтетический IPv4 и IPv6 `::` для STUN, а рабочего IPv6-маршрута по умолчанию на колонке не было.

- Отдельный минимальный UDP-тест получил корректный STUN Binding Response как через синтетический IPv4, так и через публичный адрес Google STUN. Поэтому сам синтетический адрес не признан причиной отказа UDP.
- Обычный диагностический вызов завершился `ice_gather_timeout`. Существующий параметр `ALISA_ICE_BIND_ADDRESS`, установленный в текущий IPv4 колонки только для диагностического процесса, позволил получить голосовой ответ. Микрофон и вывод ALSA в этом процессе не использовались.
- После исправления запуска настоящий контроллер установил голосовое соединение: подтверждены текст и звук ответа, ненулевые микрофонные кадры и ноль ALSA underrun. Проверочный разговор закрыт; сохранённый вход и настройки сохранились.

Это подтверждает работоспособность привязки к IPv4 в указанной сети. Точная внутренняя причина задержки dual-stack ICE не устанавливалась; проверка выполнена на одной колонке.

## Выбор IPv4 без привязки к старому IP

`run.sh` сохраняет явно заданный `ALISA_ICE_BIND_ADDRESS`, включая адрес TUN встроенного VLESS. Если привязки нет, он проверяет наличие исходного IPv4 командой `ip -4 route get 1.1.1.1` и задаёт клиенту `0.0.0.0` — IPv4 wildcard. Команда читает таблицу маршрутов без отправки пакетов. При отсутствии IPv4 остаётся обычное поведение клиента.

Wildcard выбирает семейство IPv4, но не закрепляет IP интерфейса на весь срок работы демона. Каждый новый ICE-агент собирает актуальные адреса интерфейсов. Поэтому смена Wi-Fi или DHCP-адреса между разговорами не оставляет старый IP в привязке. Уже открытый разговор этим изменением не переносится между сетями. Если клиент стартовал без IPv4, а сеть позже изменилась, для повторного выбора режима нужен его перезапуск.

Этот вариант добавлен при интеграции [PR #11 от softhoz](https://github.com/rison1337/Alisa-ChatGPT-voice-assistant/pull/11). Автор подтвердил работу явного IPv4 на одной Мини 2; wildcard отдельно проверен на закреплённой версии libjuice: настоящий ICE-агент возвращает текущие IPv4-кандидаты, не возвращает `0.0.0.0` как адрес кандидата и не включает IPv6. На стенде перечисление интерфейсов меняется между двумя соединениями; маршруты и адреса компьютера не изменяются. [Воспроизведение проверки](development.md#проверка-ipv4-ice-без-колонки).

Системные настройки IPv6, DNS и маршрутизации не меняются. Явная привязка VPN сохраняет приоритет; отказ туннеля не разрешает прямой выход.
